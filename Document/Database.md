## Implementation notes (differences from the first draft)

| Area                                                                          | As built                                                                                                                                                                                    |
| ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `roles`                                                                       | Has a `slug` (stable key for the 9 built-in roles, e.g. `admin.super`); built-in roles and their permissions are created by the migration (`App\Auth\SystemRoles`)                          |
| Ledger links                                                                  | Journals point to their source (`transaction_id`, `adjustment_id`, `settlement_payment_id`); `adjustments` and `settlement_payments` have **no** `journal_id` column (avoids circular keys) |
| Append-only                                                                   | Enforced twice: database triggers **and** revoked UPDATE/DELETE for the app user in production (`database/sql/app-privileges.sql`)                                                          |
| Existing dev databases                                                        | Phase 1 demo users without an organisation are attached to placeholder records `MIGRATED-P` / `MIGRATED-B`; run `make fresh` for clean demo data                                            |
| Design check (Phase 2, [Implementation-Plan.md](Implementation-Plan.md) §2.1) | D-1 customer vs bank UTR · D-2 bank + UPI on one account · D-3 limit types + branch top-ups · D-4 partner payout fields · D-5 statement entry author: all reflected in the tables below     |

## 0. Conventions

| Topic             | Rule                                                                                                                                                                                                                                                                    |
| ----------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Primary keys      | `uuid` (UUIDv7: time-ordered, generated by Laravel `HasUuids`). Never exposed in URLs to customers                                                                                                                                                                      |
| Public references | Human-readable, non-sequential: `PI-260927-8F3K2Q` (pay-in), `PO-…` (payout), `ST-…` (settlement). Unique                                                                                                                                                               |
| Money             | `bigint` **paise** (₹1 = 100). `CHECK (amount > 0)` wherever an amount must be positive. Signed only in the ledger                                                                                                                                                      |
| Commission rates  | `numeric(7,4)` **percent** (e.g. `2.5000` = 2.5%), `CHECK (rate BETWEEN 0 AND 100)`. Commission = `round_half_up(amount × rate / 100)` to whole paise, stored as `bigint` (Req G-04)                                                                                    |
| Time              | `timestamptz` everywhere (stored UTC). The **business date** (daily limits, daily settlement) uses Asia/Kolkata, stored as a `date`                                                                                                                                     |
| Enumerations      | `text` + `CHECK (col IN (…))`, mirrored by PHP enums. Easier to evolve than Postgres ENUM types                                                                                                                                                                         |
| Sensitive data    | Account numbers, UPI IDs, API secrets: Laravel encrypted casts (`text`). Uniqueness and search use a separate `…_hash` column (HMAC-SHA256 with a dedicated key, `PAYGATE_HASH_KEY`, see Deployment.md §2.1; `App\Support\Crypto\BlindIndex`), and lists show `…_last4` |
| Append-only       | `transaction_events`, `ledger_journals`, `ledger_entries`, `audit_logs`, `security_logs`, `webhook_attempts`: a database trigger rejects UPDATE/DELETE/TRUNCATE (same pattern as Phase 1)                                                                               |
| Deleting          | Business records are never deleted, only deactivated or suspended. Foreign keys default to `RESTRICT`                                                                                                                                                                   |
| Tenancy           | Every partner- or branch-owned row carries `partner_id` and/or `branch_id`. All portal queries are scoped by the logged-in user's `partner_id` / `branch_id` in the backend (Req SEC-05)                                                                                |
| Naming            | Tables plural snake_case; foreign keys `<entity>_id`; booleans `is_…` / `…_enabled`; timestamps `…_at`                                                                                                                                                                  |

## 1. Entity overview

```text
IDENTITY            users ──N:1── roles ──1:N── role_permissions          (audit_logs, security_logs, passkeys, sessions: Phase 1)
                      │ partner_id / branch_id
NETWORK             partners ──1:N── partner_api_keys, partner_ip_rules
                      │
                      └──N:M── partner_branch_mappings ──M:1── branches ──1:N── payment_accounts
                                        │
                      commission_rates (partner | branch | mapping override, effective-dated)
CUSTOMERS           partner_customers (partner's customer reference + minimal PII)
PAYMENTS            transactions (pay-in + payout) ──1:1── payment_sessions (pay-in)
                                                  ──1:1── payout_beneficiaries (payout)
                                                  ──1:N── transaction_events (append-only history)
                                                  ──1:N── files (proofs, attachments)
LIMITS              usage_counters (daily reserved/confirmed per account, branch, partner, mapping)
RECONCILIATION      statement_imports ──1:N── statement_entries ──0..1── transactions
                    reconciliation_cases (unsettled-UTR queue)
LEDGER              ledger_accounts (per partner↔branch pair + platform accounts) ──1:1── ledger_balances
                    ledger_journals ──1:N── ledger_entries  (every journal sums to zero)
SETTLEMENT          settlements ──1:N── settlement_lines (per pair) ──1:N── settlement_payments
                    adjustments (top-up, correction, chargeback, goodwill)
INTEGRATION         webhook_events ──1:N── webhook_attempts · api_request_logs
PLATFORM            settings · pages · reason_codes · verification_documents · notifications
```

| direction              | text             | `deposit` / `withdrawal`                                                                                                                                                            |
| fee_type               | text             | `percent` now; `fixed` / `slab` reserved (Req 10.1 #5)                                                                                                                              |

**Rate lookup** for a transaction: mapping override for that side → otherwise the partner (side partner) or branch (side branch) rate in force at SUCCESS time. The ids and values are snapshotted on the transaction.
**Negative margin:** if partner rate < branch rate for a direction, the UI warns and an audit entry is written. It is not blocked (Req G-07).

Status check (per direction, Req §7.1–7.2):

- `payin`: `created`, `awaiting_payment`, `payment_submitted`, `payment_detected`, `under_review`, `success`, `rejected`, `expired`, `cancelled`, `chargeback`, `refunded`
- `payout`: `created`, `validated`, `assigned`, `processing`, `success`, `failed`, `rejected`, `cancelled`, `returned`

Key indexes:

- Branch approval queue: `(branch_id, status, created_at) WHERE status IN ('payment_submitted','under_review','assigned','processing')`
- Partner lists: `(partner_id, direction, created_at DESC)`
- Admin lists: `(status, created_at DESC)`, `(created_at)`
- Expiry sweep: `(expires_at) WHERE status IN ('created','awaiting_payment')`
- **Duplicate-UTR protection:** `UNIQUE (payment_account_id, bank_utr_normalized) WHERE direction = 'payin' AND bank_utr_normalized IS NOT NULL AND status NOT IN ('rejected','expired','cancelled')`. Reused **customer** UTRs are allowed in the database and flagged by the app for review

## 3. Ledger rules

### 3.1 Sign convention

For every **position** account: **positive = the platform owes the party; negative = the party owes the platform.** Platform accounts are positive for income.

### 3.2 Postings

The examples use Partner A (6% deposit / 5% withdrawal) and Branch 1 (3% / 3%) (Req §6).

**Pay-in SUCCESS, ₹100** (journal `payin_success`)

| Account                 | Amount  |
| ----------------------- | ------- |
| partner_position (A, 1) | +94.00  |
| branch_position (1, A)  | −97.00  |
| platform_margin         | +3.00   |
| **Sum**                 | **0** ✓ |

**Payout SUCCESS, ₹90** (journal `payout_success`, option W-A)

| Account                 | Amount  |
| ----------------------- | ------- |
| partner_position (A, 1) | −94.50  |
| branch_position (1, A)  | +92.70  |
| platform_margin         | +1.80   |
| **Sum**                 | **0** ✓ |

**Settlement payment**: Branch 1 pays the platform ₹97 outside the platform (journal `settlement`): branch_position (1, A) **+97.00**, settlement_clearing **−97.00**.
**Settlement payment**: the platform pays Partner A ₹94: partner_position (A, 1) **−94.00**, settlement_clearing **+94.00**.
Over time, `settlement_clearing` equals minus the margin actually collected, which is a built-in check that the books match the external bank.

**Top-up adjustment**: Partner A gives the platform ₹10,000 outside the platform to fund payouts at Branch 1: partner_position (A, 1) **+10,000**, settlement_clearing **−10,000** (Req G-16).

**Reversal** (chargeback, returned payout): a new `reversal` journal with the original's entries negated, or partly negated, according to the responsible party chosen on the case (Req §6.7–6.8). The original is never changed.

### 3.3 Payout availability ("balance is low", Req G-15)

```text
available(partner A @ branch 1) = ledger_balances.balance − ledger_balances.reserved   (for partner_position (A, 1))
needed(payout X)                = X + partner withdrawal commission on X
payout allowed at branch 1      ⇔ available ≥ needed
```

Example: after the ₹100 deposit, A@1 = +94.00.

- A payout of ₹80 needs ₹84.00 → **allowed**.
- A payout of ₹90 needs ₹94.50 → **"balance is low"** (unless another mapped branch has enough).
- The largest possible payout is ₹89.52 (needs ₹94.00).

> **Operational note:** settling a partner's balance out to the partner reduces the balance available for that partner's payouts. Admin decides how much to settle (a partial tick is allowed), so enough can be left for withdrawals.

### 3.4 Party totals

A party's total position = the sum of its pair accounts (e.g. partner A = Σ partner_position (A, *)). Dashboards and settlements show party totals, while payouts and settlement lines work per pair.

## 4. Write paths (each is one database transaction unless stated)

**Pay-in create (API)**

1. Verify signature, IP and limits (outside the transaction).
2. `INSERT transactions (created)` + `payment_sessions` + `transaction_events`. If the unique key `(partner_id, direction, partner_transaction_id)` conflicts, return the existing row, or 409 if `request_hash` differs.

**Customer opens the page / picks a method → allocate** (Req G-30)

```sql
SELECT a.id
FROM payment_accounts a
JOIN partner_branch_mappings m ON m.branch_id = a.branch_id AND m.partner_id = :partner
JOIN branches b ON b.id = a.branch_id
WHERE m.status = 'active' AND m.is_deposit_enabled
  AND (m.effective_from IS NULL OR m.effective_from <= now())
  AND (m.effective_to   IS NULL OR m.effective_to   >  now())
  AND b.status = 'active' AND b.is_deposit_enabled
  AND a.status = 'active'
  AND <method supported by a> AND :amount BETWEEN COALESCE(a.min_amount, 0) AND COALESCE(a.max_amount, :amount)
ORDER BY a.last_allocated_at NULLS FIRST, a.id          -- round robin (Req G-29)
FOR UPDATE OF a SKIP LOCKED
LIMIT 1;
```

Then conditionally reserve `usage_counters` for the account, branch, partner and mapping (amount, count, open sessions). If any limit is hit, try the next candidate (a bounded loop). On success: set `a.last_allocated_at = now()`, set the transaction's `branch_id`, `payment_account_id`, `method` and status `awaiting_payment`, and add an event.
If `SKIP LOCKED` returns nothing, run the query **once more without** `SKIP LOCKED` (waiting a few milliseconds). Otherwise a burst could report "unavailable" just because every account was briefly locked by another customer. Only when that also finds nothing → "temporarily unavailable" + admin alert.

**Customer submits UTR or photo** → `payment_submitted` (the duplicate-UTR unique index rejects reused UTRs) + event + branch notification.

**Branch approves** (Req G-23)

1. `SELECT … FROM transactions WHERE id = :id FOR UPDATE`, and check the status is `payment_submitted` / `under_review`.
2. Look up the rates → compute commissions.
3. Update the transaction to `success` with the snapshots.
4. Lock `ledger_balances` rows in ascending id order → insert journal + entries → update balances.
5. Move `usage_counters` from reserved to confirmed; decrement open sessions.
6. Insert `webhook_events` + `transaction_events` + `audit_logs`.
7. Commit (the zero-sum trigger checks the journal).

**Branch rejects / session expires** → status change, release the reserved counters, event, webhook. No ledger entries.

**Payout create (API)** (Req G-15, G-17)

Step 1: candidate branches in round-robin order (**no lock**; balances are only read):

```sql
SELECT m.id AS mapping_id, m.branch_id, la.id AS partner_account_id
FROM partner_branch_mappings m
JOIN branches b          ON b.id = m.branch_id
JOIN ledger_accounts la  ON la.kind = 'partner_position' AND la.partner_id = m.partner_id AND la.branch_id = m.branch_id
JOIN ledger_balances bal ON bal.ledger_account_id = la.id
WHERE m.partner_id = :partner AND m.status = 'active' AND m.is_withdrawal_enabled
  AND b.status = 'active' AND b.is_withdrawal_enabled
  AND :amount BETWEEN COALESCE(b.withdrawal_min_amount, 0) AND COALESCE(b.withdrawal_max_amount, :amount)
  AND bal.balance - bal.reserved >= :needed
ORDER BY m.last_payout_assigned_at NULLS FIRST;
```

Step 2: for each candidate in order, try to **reserve atomically**:

```sql
UPDATE ledger_balances
SET reserved = reserved + :needed, updated_at = now()
WHERE ledger_account_id = :partner_account_id
  AND balance - reserved >= :needed
RETURNING ledger_account_id;
```

The first row returned wins. This row lock is held only until commit, so parallel payouts **wait briefly instead of failing**. (With `SKIP LOCKED` here, two simultaneous payouts against one branch would wrongly get "balance is low".) Then reserve the branch withdrawal counter, set `m.last_payout_assigned_at`, and insert `transactions (assigned)` + `payout_beneficiaries` + event.
No candidate succeeds → reject with **"balance is low"**.

**Branch completes a payout** → lock the transaction → `success` + UTR → journal (§3.2) → `reserved −= needed` → counters → webhook, event, audit.
**Payout fails** → `failed` → `reserved −= needed` → webhook.

**Admin ticks settled** → insert `settlement_payments` → `settlement` journal per line → update `settled_amount` / status (`partially_settled` / `settled`) → audit.

## 5. Integrity and concurrency rules

1. **Short transactions.** No HTTP calls, emails or file I/O inside a database transaction.
2. **Lock order.** Transaction row → usage counters → ledger balances (ascending id). The same order everywhere prevents deadlocks.
3. **`SKIP LOCKED` only where skipping is harmless**: choosing among many payment accounts (with a waiting retry, §4). **Never on balance rows**; money checks use conditional updates that wait.
4. **Conditional updates** for limits: never read-then-write.
5. **Unique constraints** are the last line of defence: idempotency, duplicate UTR, double booking of a transaction, duplicate statement rows or files.
6. **The zero-sum trigger** on journals, and the append-only triggers on history tables.
7. **Status changes** go through one state-machine service using `UPDATE … WHERE status = :expected`.
8. **Nightly checks:** ledger re-sum vs `ledger_balances`; `usage_counters` vs transactions; `settlement_clearing` vs recorded settlements.

**Known hot spot:** the partner-level daily `usage_counters` row is updated by every pay-in of that partner. At the expected scale (tens of requests per second) that is fine because each lock lasts milliseconds. If a very large partner appears, its counter can be split into N shard rows.

## 8. Design choices to confirm (technical, not business)

| #   | Choice                                                                                    | Why                                                                                            |
| --- | ----------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| D-1 | One `transactions` table for pay-in **and** payout, with direction-specific status checks | Shared reports, ledger links and UTR handling; payout-only data sits in `payout_beneficiaries` |
| D-2 | Ledger accounts **per partner↔branch pair**                                               | Required by the pair-level payout balance (G-15); party totals are sums                        |
| D-3 | Commission rates as effective-dated rows + an exclusion constraint                        | History and audit of offline-negotiated rates (G-06); no overlaps possible                     |
| D-4 | Rates as `numeric(7,4)` percent, commissions rounded half-up to paise per transaction     | Exact and simple (G-04)                                                                        |
| D-5 | Settlement lines per pair, header per party                                               | Settlement ticks keep pair balances (and payout availability) correct                          |
| D-6 | Encrypted columns + HMAC hash columns for bank/UPI numbers and API secrets                | Protects data at rest while keeping uniqueness and search                                      |

After approval: migrations in this order: roles/users changes → partners/branches/mappings/rates → payment accounts/usage → customers/transactions/sessions/events/files → ledger → reconciliation → settlement/adjustments → webhooks/logs → platform tables. Each step ships with tests for its constraints (zero-sum, duplicate UTR, idempotency, limits).
